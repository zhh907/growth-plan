一、上次三问的答案

Q1:容器跑在谁肚子里
跑在 OrbStack 内部的 Linux 虚拟机里。Pod 只是 k8s 数据库里的一条记录;真正起容器的是虚拟机里的 containerd。
破案:进程表里找不到 kubelet,是因为 OrbStack 的 k8s 是 k3s——把 kubelet、api-server 等全部打包进一个叫 k3s 的程序。
Q1: WHERE DO CONTAINERS LIVE
Inside OrbStack's internal Linux VM. A Pod is just a record in k8s' database; the actual work is done by containerd in the VM.
Case solved: no process named "kubelet" exists because OrbStack's k8s is k3s — one binary bundling kubelet, api-server and friends.
Q2:Events 像什么
像后端服务的日志:带时间戳、只追加、按时间排。Pod 出问题先 kubectl describe 翻 Events,从最后一条 Warning 往上找原因——和查日志一个套路。
Q2: WHAT EVENTS RESEMBLE
Backend service logs: timestamped, append-only, time-ordered. When a Pod misbehaves, read Events in kubectl describe bottom-up — same habit as reading a log file.
Q3:Pod IP 和 Mac 的关系
没关系。Pod IP 由 CNI 插件从 cni0 网桥的网段发(192.168.194.x),这个网络只存在于虚拟机内部。实测 Mac 直接 curl Pod IP:等满 75 秒超时。
超时 = 包被丢弃(路由不通);秒拒 = 包到了但端口没人听。失败模式本身就是诊断信息。
Q3: POD IP vs MAC IP
No relation. Pod IPs come from the cni0 bridge segment (192.168.194.x), which exists only inside the VM. Tested: curl from Mac to a Pod IP timed out after 75s.
Timeout = packets dropped (no route); instant refusal = arrived but port closed. The failure MODE is itself a diagnostic.

二、钻进节点看到的三样东西

进入方式:kubectl debug node/
节点虚拟机不开放 SSH(OrbStack 的 ssh orb 只进用户自建的机器)。要看节点内部,用 kubectl debug node/orbstack -it --image=busybox:起一个共享宿主进程表的调试容器,就能看到节点的进程和网卡。用完记得删。
ENTRY: kubectl debug node/
The node VM has no SSH (OrbStack's ssh orb only reaches user-created machines). Use kubectl debug node/orbstack -it --image=busybox: a debug pod sharing the host's process table, so node processes and interfaces are visible. Delete it when done.
① containerd-shim:每个容器一个"养父"进程
进程表里每个容器对应一个 shim。容器死了 shim 负责收尸,containerd 本体不受牵连。7 个 shim = 7 个容器。
① containerd-shim: A FOSTER PARENT PER CONTAINER
Each container maps to one shim process. When a container dies, the shim reaps it so containerd itself never goes down. 7 shims = 7 containers.
② pause 容器:Pod 网络的真正主人
每个 Pod 先起一个几乎不耗资源的 pause 容器,由它持有网络命名空间(拿 IP)。Pod 里的其他容器加入它——这就是同一 Pod 内容器共享 IP 和 localhost 的实现。
② pause CONTAINER: THE REAL OWNER OF A POD'S NETWORK
Each Pod first starts a near-zero-cost pause container that holds the network namespace (gets the IP). Other containers join it — this is how containers in one Pod share IP and localhost.
③ 自己的 Tomcat 还在里面跑着
进程表第 381 行是一个 Java 8 Tomcat——以前 docker 起的,挂在 docker 网桥上,和 k8s 的 Pod 网络互不相干。同一台虚拟机里,docker 世界和 k8s 世界各用各的网段。这只 Tomcat 以后就是 Docker 单元的活教材。
③ MY OWN TOMCAT STILL RUNNING (PID 381)
Line 381 is a Java 8 Tomcat started long ago via docker, sitting on a docker bridge — untouched by, and unrelated to, the k8s Pod network. Two worlds, one VM, separate subnets. This Tomcat becomes the living textbook for the upcoming Docker unit.

三、第一个 Deployment + Service

两个新对象,各管一件事
Deployment:你声明"要 2 个 Pod",它盯着现实,少了补、多了删(自愈)。
Service:一个不变的地址,转发给后面的 Pod。Pod 换 IP 它自动跟踪,靠的是 label 选择器。
TWO NEW OBJECTS, ONE JOB EACH
Deployment: you declare "I want 2 Pods"; it watches reality and fixes any gap (self-healing).
Service: a stable address forwarding to its Pods. It tracks IP changes automatically via label selectors.
途中修了一个真实报错
cannot unmarshal string into ... replicas of type int32 YAML 按写法定类型:2 是数字,"2" 是字符串。k8s 服务端是强类型,报错会写明哪个字段、期望什么类型——读懂就不用猜。
另学到:apply 按对象逐个处理,不成事务——Service 成了、Deployment 失败,是正常现象;重跑幂等。
ONE REAL ERROR, FIXED
cannot unmarshal string into ... replicas of type int32 YAML types come from syntax: 2 is a number, "2" a string. The k8s API is strongly typed server-side, and errors name the field and expected type — read them instead of guessing.
Bonus: apply is per-object, not a transaction — Service created while Deployment failed is normal; re-applying is idempotent.
localhost:30080 到 nginx:共 5 层
① OrbStack 把 Mac 的 30080 映射进虚拟机 → ② 节点的 nodePort 被 iptables 规则认出 → ③ DNAT 改写成某个 Pod IP:80 → ④ 包经 cni0 网桥进入 Pod 的网络命名空间 → ⑤ nginx 收到。
关键认知:Service 的 IP 没有进程在监听,它只是 iptables 规则造出的虚拟地址。
localhost:30080 → nginx: 5 HOPS
① OrbStack maps Mac's 30080 into the VM → ② iptables rules recognize the nodePort → ③ DNAT rewrites the destination to some Pod IP:80 → ④ the packet crosses cni0 into the Pod's network namespace → ⑤ nginx answers.
Key fact: nothing listens on a Service IP — it is a virtual address invented by iptables rules.
