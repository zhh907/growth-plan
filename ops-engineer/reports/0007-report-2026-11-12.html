一、今天的三个概念 Three Ideas, Told with Examples

每个概念配一个你熟悉的例子 · Each idea comes with an example you already know
1 · 入口层四阶梯:从"只在内部可达"到"一个总机分流"
集群里的服务想被外面访问,有四档:ClusterIP 只在集群内可达(api 就是这种);NodePort 在节点上开一个端口,一个服务吃一个口(web 的 30081);Ingress 只留一个总机,按域名/路径把流量分给各个服务;再往上是云厂商的 LoadBalancer。
用你的行当打比方:ClusterIP 是内部电话,NodePort 是每个部门开一个对公窗口,Ingress 是前台总机——客户只记一个号码,报名字转分机。你现在站在第三档。
1 · THE EXPOSURE LADDER: FROM INSIDE-ONLY TO ONE SWITCHBOARD
A service can reach the outside world in four grades: ClusterIP, in-cluster only (that's service/api); NodePort, one port per service (web's 30081); Ingress, a single switchboard routing by host and path; and above that, a cloud LoadBalancer.
In your own trade's terms: ClusterIP is an internal line, NodePort gives every department its own public window, and Ingress is the front desk — customers memorize one number and ask for a name. You stand on the third rung now.
2 · 纸和总机:Ingress 资源不是 Ingress 控制器
这是 Ingress 排第一的坑:Ingress 资源只是一张路由表(几行 YAML:"/api → api 服务"),必须有一个真正干活的 Pod 去读它并执行转发——那就是 Ingress Controller(我们装的 ingress-nginx)。
没有控制器,你写一百张路由表也没人看。所以顺序永远是:先请总机(装 Controller),再给总机递表(写 Ingress)。你的 show 里先查了 kube-system 确认没有现成总机(OrbStack 的 k3s 把自带的 Traefik 关了),再安装——这个"先查再动手"救了你一次。
2 · THE PAPER AND THE SWITCHBOARD: INGRESS RESOURCE ≠ INGRESS CONTROLLER
The number-one Ingress trap: an Ingress resource is just a routing table — a few lines of YAML ("/api → service api") — and someone must actually read it and forward traffic. That someone is the Ingress Controller (the ingress-nginx we installed).
No controller, and a hundred routing tables sit unread. So the order is always: hire the operator first, then hand over the sheet. Today you checked kube-system and found no operator (OrbStack's k3s keeps its bundled Traefik switched off) — that "verify before assuming" check saved you once already.
3 · Service 是标签契约,真身永远是 Pod IP:端口
describe 里那一行 /api api:80 (192.168.194.21:5678) 值得盯三秒:括号里是总机解析后的真实目的地——Pod IP + 5678。5678 是 http-echo 容器自己监听的端口,不是 Service 的 80。Service 只是写在标签上的契约("app=api 的 Pod 都算我的人"),转发时走的是 Pod 的真地址。
这也解释了当年僵尸 Pod 劫持事件:契约只认标签,不查户口。
3 · A SERVICE IS A LABEL CONTRACT; THE BODY IS ALWAYS POD IP:PORT
Give this describe line three seconds: /api api:80 (192.168.194.21:5678) — the parenthesized part is the controller's resolved target: Pod IP plus 5678, the port the http-echo container itself listens on, not the Service's 80. The Service is merely a contract written on labels ("every Pod with app=api is mine"); traffic rides on the Pod's true address.
Which also explains the zombie-Pod hijack from before: the contract checks labels, never lineage.

二、今日一战 Today's Battle: `web-svc` NotFound, Twice

症状 → 根因 → 教训,数字说话 · Symptom → root cause → lesson, told with numbers
病状:删除命令报"找不到",连报两次
清场第一步 kubectl delete service web-svc → Error from server (NotFound),重跑一次,还是 NotFound。
根因:这个 Service 在本场更早的时候已经被删过一次(当时命令输出没有贴出来)。两次 NotFound 不是两条错误,是同一个事实被复述了两次:目标状态早已达成。
教训:删除类命令的 NotFound = "你要删的东西不在" = 结果已经正确,重启不了任何东西,重跑也安全(声明式工具不介意)。别追着命令的提示跑,相信终态查询——随后 kubectl get pods,svc,ingress 给出全图:2 Pod / 3 Service / 1 Ingress,干净收场。
SYMPTOM: THE DELETE SAID "NOT FOUND" — TWICE
First cleanup step: kubectl delete service web-svc → Error from server (NotFound); re-run, NotFound again.
Root cause: the Service had already been deleted earlier in this very session (that output was never pasted). Two NotFounds are not two errors — they restate one fact twice: the desired state was already achieved.
Lesson: NotFound on delete means "the thing you want gone is gone" — the outcome is already correct, nothing restarts, re-running is safe (declarative tooling doesn't mind). Don't chase the command's message — trust the final-state query. The following kubectl get pods,svc,ingress drew the whole picture: 2 Pods / 3 Services / 1 Ingress, clean exit.

三、Today's English 今天遇到的英语

只收今天真实碰到的 · Drawn only from today's real encounters — click the right column to listen
① describe — 描述;给对象调档案
你今天亲自问的词。de(完全)+ scribe(写)= 完整写下来。同根一家:scribe 抄写员、prescribe 开处方、subscribe 订阅、script 脚本。
命令语义:kubectl get 是点名册(几列摘要),kubectl describe 是人事档案(规格 + 状态 + 最近事件流水)。排障顺序永远是:get 发现不对劲 → describe 看 Events 找原因。
① DESCRIBE
The word you asked about yourself. De (fully) + scribe (write) = write it all down. One family: scribe, prescribe, subscribe, script.
Command semantics: kubectl get is a roll-call table (a few summary columns); kubectl describe is the full HR file (spec + status + recent events). Troubleshooting order is fixed: get shows something off → describe reads the Events for why.
② ingress — 入口;进入
动词 ingress = 进入(比 enter 更书面,常说 ingress of air 空气进入);名词 = 入口。网络语境里,ingress traffic = 入站流量,egress traffic = 出站流量(一对反义词,云账单和防火墙规则里天天见)。
Kubernetes 把 "Ingress" 专名化为那个负责入站路由的对象——名字本身就是它的职责:管进来的人。
② INGRESS
As a verb, ingress = to enter (more formal than enter; "the ingress of air"). As a noun = an entrance. In networking: ingress traffic = inbound, egress traffic = outbound — a pair you meet daily in cloud billing and firewall rules.
Kubernetes capitalized "Ingress" into the object responsible for inbound routing — the name IS the job: managing who comes in.
③ endpoint — 端点;一条路由的终点
end(终点)+ point(点)。在网络里,endpoint = 通信的另一头(一个 IP:端口就是一个 endpoint)。你的 describe 表里括号中 192.168.194.21:5678 就是一个 endpoint。
k8s 里 Endpoints 对象是 Service 背后真实 Pod 地址的实时清单——Pod 增减,它跟着变。Service 是名字,Endpoints 是名单。
③ ENDPOINT
End + point. In networking, an endpoint is the far side of a connection — one IP:port. In your describe table, 192.168.194.21:5678 is one endpoint.
In Kubernetes, the Endpoints object is the live roster of real Pod addresses behind a Service — Pods come and go, the roster follows. The Service is the name; Endpoints is the list.
④ baremetal — 裸金属;没有云的机器
你安装用的清单叫 provider/baremetal/deploy.yaml。bare = 裸的,metal = 金属(铁皮机器)。云圈用它讽刺性地区分:baremetal = 真实物理机(或本机集群),相对于跑在别人云平台上的机器。
选这个清单的原因:它在我们的 OrbStack 集群上直接给 NodePort,不需要云厂商的负载均衡器——"没有云"的部署姿势。
④ BAREMETAL
The manifest you installed is provider/baremetal/deploy.yaml. Bare = naked, metal = the iron box. Cloud folks use it to distinguish: baremetal = a real physical box (or a local cluster), as opposed to machines running on someone else's cloud.
That variant was the right pick because it hands out NodePorts directly on our OrbStack cluster — no cloud load balancer involved. Deployment for the "no cloud" world.
