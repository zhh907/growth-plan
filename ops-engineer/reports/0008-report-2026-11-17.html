一、今天的五个概念 Five Ideas, Told with Examples

每个概念配一个你熟悉的例子 · Each idea comes with an example you already know
1 · cgroup = 电表:三种超限,三种死法
namespace 是墙(决定看得见什么),cgroup 是表(决定用得多少)。三种资源超限,后果完全不同:内存超限 处决(OOM kill,SIGKILL,退出码 137);CPU 超限 掐表(挂起等下个周期,卡而不死,可逆);进程数超限 拒生(fork 直接报错,已有的不杀)。limits.memory limits.cpu 写的 yaml,最后都落到这三个文件上。
1 · CGROUP = THE METERS: THREE RESOURCES, THREE DEATHS
Namespace is the wall (what you can see); cgroup is the meter (how much you may use). Three resources, three different deaths: memory over limit is execution (OOM kill, SIGKILL, exit code 137); CPU over quota is throttling (suspended till next period — slow, not dead, reversible); process count over pids.max is refused birth (fork returns an error, existing processes untouched). The limits.memory and limits.cpu lines in your yaml all land on these files.
2 · 旋钮不是自带的:父组下放才长出来
你 mkdir 了子组,里面却没有 pids.max——不是权限问题,是 cgroup v2 的控制器要父组在 subtree_control 里签发,子组才长出对应旋钮文件。echo +pids > cgroup.subtree_control 一敲,test/ 里立刻长出 pids.max。像分行开权限:总行不授权,支行办不了这项业务。
2 · KNOBS ARE NOT BUILT-IN: PARENT MUST DELEGATE
You mkdir'd a child group and found no pids.max inside — not a permission problem, but the cgroup v2 rule: the parent must enable the controller in subtree_control before the child grows those knob files. One echo +pids > cgroup.subtree_control, and pids.max appeared in test/. Like a bank branch: without headquarters' authorization, the branch cannot offer that service.
3 · chroot = 换地板,墙和账都不动
chroot 进毛坯目录后,$$ = 54 还是原来的号码——地板换了,PID 楼没换。而且毛坯房里连 bash 都没有:得把 bash、它依赖的动态库(ldd 列出的那些)、还有加载器 ld-linux 一起搬进去。bash 明明在,却报 "No such file or directory"——那说的不是 bash,是加载器。这个报错今天骗到你一次,以后骗不到了。
3 · CHROOT = NEW FLOOR; WALLS AND LEDGER UNTOUCHED
After chroot into the bare directory, $$ = 54 — the old number, because the floor changed, the PID building did not. And the bare room has no bash: you must carry in bash, its shared libraries (the ones ldd lists), and the loader ld-linux. "No such file or directory" while bash clearly exists — the message is about the loader, not bash. It fooled you once today; it won't fool you again.
4 · 容器 = 墙 + 账 + 地板,三柱亲手装齐
最终形态三行:unshare --pid --fork --mount 砌墙,mount -t proc proc /myroot/proc 记账,chroot /myroot 换地板。进去后 $$ = 7,/proc/self 也是 7——两本账第一次完全一致。为什么是 7 不是 1?因为 1 号是托住房间的门外 bash,你脚下这个是它的后代。docker run 拆到底,就是这三件事加自动化。
4 · A CONTAINER = WALLS + LEDGER + FLOOR, ALL BY HAND
The final form is three lines: unshare --pid --fork --mount raises the walls, mount -t proc proc /myroot/proc keeps the ledger, chroot /myroot swaps the floor. Inside, $$ = 7 and /proc/self reads 7 too — the two ledgers finally agree. Why 7 and not 1? Because PID 1 is the outer bash holding the room; the one under your feet is its descendant. Strip docker run to the bone and it is these three moves plus automation.
5 · 挂载的可见性,在记账那刻就定了
一行命令版造容器失败:/proc 是空的。根因:--mount-proc 把挂载记在了旧树的 /proc 路径上,然后 chroot 才换地板——账本上的条目跟着路径走,地板一换就够不着了。这正是 L2 讲过的定律换了个方向再咬人一次:可见性绑定在记账时的路径。修法不是换工具,是换顺序:先在新地板的路径上记账,再换地板。
5 · MOUNT VISIBILITY BINDS AT RECORDING TIME
The one-liner container failed: /proc came up empty. Root cause: --mount-proc recorded the mount on the old tree's /proc path, and only then did chroot swap the floor — a ledger entry follows its path, and a floor swap leaves it behind. It is the L2 law biting from a new angle: visibility binds to the path at the moment of recording. The fix was not a different tool but a different order: record on the new floor's path first, swap the floor second.

二、今日一战 Today's Battle: The Empty /proc

症状 → 根因 → 修复,数字说话 · Symptom → root cause → fix, told with numbers
病状:PID 1 当上了,/proc 却是空的
unshare --pid --fork --mount-proc chroot /myroot /bin/bash 跑完,$$ = 1 对了,但 echo /proc/* 原样吐回、/proc/self/stat 不存在。新楼的新账本,花名册没了。
推理三步:mount 挂载是 rw(排除只读)→ --mount-proc 的执行时机在 chroot 之前 → 条目记在旧树路径上,换地板后不可达。修复三行:mkdir 新地板的 /proc 洞 → mount 直接记在 /myroot/proc → 再 chroot。结果 read < /proc/self/stat 出 7,echo $$ 也是 7。
同场加映:cgroup 的 echo $$ > cgroup.procs 报 EOPNOTSUPP,PID 1 假设被 sleep 实验证伪——这桩悬案挂着,判别实验已经备好,下次开场就办。
SYMPTOM: PID 1 AT LAST, /PROC EMPTY
After unshare --pid --fork --mount-proc chroot /myroot /bin/bash, $$ = 1 was right, but echo /proc/* echoed the glob back and /proc/self/stat did not exist. The new building's new ledger had no roster.
Three-step reasoning: the mount is rw (read-only ruled out) → --mount-proc runs before the chroot → the entry lives on the old tree's path, unreachable after the floor swap. Fix, three lines: mkdir the /proc hole on the new floor → mount directly onto /myroot/proc → chroot last. Result: read < /proc/self/stat yields 7, and echo $$ says 7.
Same sitting, a cliffhanger: writing to cgroup.procs returned EOPNOTSUPP, and the PID-1 hypothesis was falsified by moving a sleep process instead. The case is parked with a discriminating experiment ready — first order of business next session.

三、Today's English 今天遇到的英语

只收今天真实碰到的 · Drawn only from today's real encounters — click the right column to listen
① throttle — 掐表限流
cpu.max 超限的官方动词。nr_throttled = 被掐的次数。本义是油门/节流阀:发动机不熄火,只是踩不到底。对比记忆:throttle 卡而不死,OOM kill 直接处决——CPU 可回收,内存收不回,所以手段一软一硬。
① THROTTLE
The official verb for exceeding cpu.max; nr_throttled counts the times you were throttled. Literal sense: a throttle valve — the engine keeps running, you just can't floor it. Contrast to memorize: throttling stalls without killing; OOM kill executes — CPU is reclaimable, memory is not, hence one soft tool and one hard.
② OOM kill — 内存耗尽处决
OOM = out of memory,内核的最后一道手段:挑组里最肥的进程发 SIGKILL。退出码 137 = 128 + 9(9 是 SIGKILL 的编号)。运维看到 137,第一反应就该是"内存超了",就像交易员看到特定错误码就知道是哪家流动性商拒单。
② OOM KILL
OOM = out of memory; the kernel's last resort: pick the fattest process in the group and SIGKILL it. Exit code 137 = 128 + 9 (9 is SIGKILL's number). An ops engineer seeing 137 should think "memory over limit" first — the way a trader reads a specific reject code and knows which liquidity provider said no.
③ EOPNOTSUPP — Operation not supported
今天 cgroup.procs 写入的报错。Linux 错误码全家都长这样:E 前缀 + 大写缩写:ENOENT(No such file,文件不存在)、EACCES(Permission denied,权限不够)、EAGAIN(Resource temporarily unavailable,fork 被拒就是它)。读报错先认前缀,像看盘先看品种代码。
③ EOPNOTSUPP — OPERATION NOT SUPPORTED
Today's error from writing cgroup.procs. The Linux errno family all look like this: E prefix + abbreviation. ENOENT (no such file), EACCES (permission denied), EAGAIN (resource temporarily unavailable — what a refused fork gets). Read the prefix first, the way you read the symbol code before the price.
④ pivot_root — 转轴换根
pivot = 枢轴(篮球的转身脚不许挪,那个动作就叫 pivot)。pivot_root 不是换个参照点,是把整棵挂载树绕着轴挪走,旧根真正不可达。chroot 有个老漏洞:有 root 权限可以 chroot 两次逃回旧根。生产容器用 pivot_root,就是堵这条逃生通道。
④ PIVOT_ROOT
Pivot = the basketball move where one foot stays planted. pivot_root does not merely change a reference point — it swings the whole mount tree around that axis, leaving the old root genuinely unreachable. chroot has an old flaw: with root privilege, a double chroot can escape back. Production containers use pivot_root to close that escape hatch.
⑤ delegation — 委托/授权
mount 输出里的 nsdelegate:权限按"这个组是否过户给你"判,不按 root 身份判。住在房间里 ≠ 可以改电表;要房本过户(文件 owner 改成你)才算真授权。银行同款:你是客户 ≠ 你能动客户的账。
⑤ DELEGATION
From today's mount output, nsdelegate: permission is decided by whether the group is deeded over to you, not by being root. Living in the room does not mean you may touch its meters; the deed must be transferred (the files' owner set to you). Banking works the same: being the customer's son is not being the account holder.
