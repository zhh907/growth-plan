二、0004 学到的三个点

1. 循环包成函数,用 return 不用 print
run_agent() 把答案作为值返回。谁调用谁决定怎么用:今天在终端打印,明天接 Web 服务直接返回 JSON,循环代码一行不用改。撞上限没拿到答案就返回 None,让调用方知道失败。
1. WRAP THE LOOP IN A FUNCTION; RETURN, DON'T PRINT
run_agent() returns the answer as a value. The caller decides what to do: print it today, return JSON from a web service tomorrow — the loop code stays untouched. No answer after the round cap → return None so the caller knows it failed.
2. 退出码 = 程序结束时报告的数字
0 = 成功,1 = 运行出错,2 = 参数写错(argparse 自动给)。脚本和定时任务、CI 靠这个数字判断成败。报错但退出 0 = 在流水线里假装成功,会坑下游。
2. EXIT CODE = THE NUMBER A PROGRAM REPORTS WHEN IT ENDS
0 = success, 1 = runtime failure, 2 = usage error (argparse gives this for free). cron and CI judge success by this number. Printing an error but exiting 0 = fake success that breaks downstream jobs.
3. 报错走 stderr,不走 stdout
管道命令 | 只传递 stdout。报错写进 stdout 会流进下一个命令,比如 jq 收到一句报错文本就崩。写 stderr 则报错直达屏幕,数据通道保持干净。
3. ERRORS GO TO stderr, NOT stdout
A pipe | only carries stdout. An error printed to stdout flows into the next command — e.g. jq chokes on a plain-text error line. stderr goes straight to the screen and keeps the data channel clean.

三、0005 学到的三个点

1. 为什么不把整个文件塞给模型
每一轮都重发全部历史,全部计费。千行文件一次读入,后面每轮都为它重复付费。而且上下文一长,模型对中段内容的记忆变差——bug 偏偏藏在细节里。所以按需分段读。
1. WHY NOT SEND THE WHOLE FILE TO THE MODEL
Every round resends the entire history, and you pay for all of it. Read a 1000-line file once and you keep paying for it every round. Long context also weakens recall of the middle — exactly where bugs hide. So: read in chunks, on demand.
2. 工具返回的每行都带行号
模型要报"第 N 行有 bug",前提是它知道每行是第几行。行号由工具加([42] if(...)),不靠模型数。报告行号的依据就在这。
2. EVERY LINE THE TOOL RETURNS CARRIES ITS NUMBER
To report "bug at line N", the model must know N. The tool adds the numbers ([42] if(...)) — never rely on the model to count. This is what makes line-cited findings possible.
3. 出错返回 dict,不抛异常
工具出错时返回 {"error": "..."},这段文本会回传给模型。错误信息里写清原因和正确答案(如 "total 91 lines"),模型下一轮自己改参数重试。测试这层不需要调 API,零成本。
3. RETURN ERRORS AS DICTS, DON'T RAISE
On bad input the tool returns {"error": "..."}, which goes back to the model. If the message states the cause and the right answer (e.g. "total 91 lines"), the model fixes its own args next round. Testing this layer needs zero API calls.

五、词汇表 Vocabulary

CLI 工程
exit code 退出码 — 程序结束时报告成功/失败的数字
stderr / stdout — 错误信息通道 / 正常数据通道,管道只传后者
positional argument 位置参数 — 按顺序传入的必填参数
nargs="+" — 把多个词收进一个列表;用户忘加引号也不会崩
CLI ENGINEERING
exit code — the number a program reports on exit
stderr / stdout — error channel vs data channel; pipes carry the latter only
positional argument — required argument passed by position
nargs="+" — collect multiple words into one list; survives unquoted input
上下文与成本
context window 上下文窗口 — 模型一次能读的全部内容,按 token 计费
lost in the middle — 上下文很长时,中段内容容易被模型忽略
tool granularity 工具粒度 — 一次调用返回多少内容的设计选择
CONTEXT & COST
context window — everything the model can see at once; billed in tokens
lost in the middle — in long contexts, mid-file content gets overlooked
tool granularity — how much one tool call returns; a design choice
设计模式
errors-as-data 错误即数据 — 错误放进返回值,让模型读了自己纠错
clamp / reject — 超出范围就收缩(如读到文件尾)/ 参数逻辑错误就拒绝
entry guard 入口守卫 — if __name__ == "__main__",被 import 时不执行主逻辑
DESIGN PATTERNS
errors-as-data — put errors in the return value so the model can self-correct
clamp / reject — shrink out-of-range values (e.g. clamp to EOF) / refuse structurally wrong args
entry guard — if __name__ == "__main__": main logic skipped on import
